# lesson-prep-skills

面向中小学教师的备课技能包，可被罗湖教育云 Harness、Claude Code 等支持 Skill 机制的 AI 平台加载。

## 技能列表

| 技能 | 说明 |
|---|---|
| [`lesson-prep-three-align`](skills/lesson-prep-three-align/SKILL.md) | 三对齐·四步闭环备课法：三对齐（课标／教材／学情）＋学科教案模板适配＋「定标·设计·配评·回流」四步闭环 |

## 在罗湖教育云 Harness 中使用

1. 打开 `技能市场` → `网络技能市场`
2. 在「按仓库浏览」填入本仓库的 `GitHub 用户名/仓库名`，分支 `main`
3. 点「拉取技能列表」→ 找到 `lesson-prep-three-align` → 一键存入「我的技能」

也可以直接下载 `skills/lesson-prep-three-align/SKILL.md`，在 `学校技能市场` 右上角上传共享。

## 配套语料

本技能本体不含任何学科专属内容，学科差异全部通过知识库文件承载：

| 语料 | 必需 | 说明 |
|---|---|---|
| 课程标准 | 是 | 对应学科的课标全文 |
| 教材 | 是 | 要备的单元即可，不必传全册 |
| 学科教案模板 | 是 | 格式见 SKILL.md 附录 B 的元信息表头 |
| 学情档案 | 建议 | 模板见 SKILL.md 附录 A |
| 优秀教学设计样例 | 可选 | 3—5 份即可 |

v1.1.0 的改动来自一个实践中发现的问题：AI 生成内容后教师仍需手工重排为区定教案模板，**格式返工成为备课的「最后一公里」隐性成本**，且这部分耗时长期被算在「备课时长」之外，没有单独计量过。

v1.2.0 的改动全部来自**第一次真实课堂试用的 13 轮对话日志**。技能本体的铁律（决策点、留痕、缺料即停）经受住了检验，失效的是执行细节：助手只检索了工作区目录就断言"模板未上传"，而模板一直在知识库里，空转 4 轮；知识库同时存在通用版与学科版模板时选错了通用版；成品连出两轮 Markdown 中间稿；装配阶段用脚本从零重建 Word 版式而非在原件上填空，单轮消耗 26 次模型调用。另有一处更隐蔽的问题：一条标注为"二手来源、需核实"的课标引用，在后续轮次的转述中被升格为"知识库权威来源"——**来源标注会在多轮传递中被洗白**，这对"数据真实可追溯"是实质风险，故新增标注传递规则。

v1.3.0 来自两条独立证据的交叉验证。

其一是**成品与模板的结构比对**：官方模板的「课前备课要素表」是一张 16 行 × 9 列、含多重合并的表格，而助手产出的成品把它拆成了 8 行 × 2 列的小表加 64 个自由段落——内容齐全、栏目不缺，但承载结构完全不同。同时出现两类静默偏差：模板中标注「此栏目为推荐标准，不改动」的栏目被改写甚至改名，而本该被替换掉的淡红色说明文字却被当作栏目名保留了下来。**该删的留着，该留的改了。** 根因是 v1.2 只写了"在原件副本上填写"这条原则，没有给出可执行路径，助手只能退回到"理解内容后重写一份"。而这类失败助手无法自我察觉——文档读起来完全正常，必须靠机械的结构比对才能发现。

其二是**助手对本技能的自评**。它指出 v1.2 假设了一个它并不具备的能力：平台的知识库是以参考资料形式被动注入对话的，不存在可主动调用的检索动作，而 v1.2 不仅要求"先检索知识库"，还给出了 `已检索：知识库（命中 2 份模板）` 这样的示范句——等于为虚假报告提供了模板。它同时指出来源分级缺少「官方配套文件」一档，使《义务教育信息科技课程教学指南》这类权威材料无处归类，只能被降格或升格——这正是 v1.2 观察到的"标注洗白"现象的结构性成因，此前被误判为单纯的转述丢失。

自评中未采纳的一条：助手建议为决策点增加"教师连续 2 轮未回应即按默认方案推进"的超时降级。该提议被驳回——决策点是「AI 只辅助不代写」的唯一落地机制，可自动默认即等于取消，且会话悬挂对教师并无成本。改为：决策悬置时先产出不依赖该决策的栏目并明示悬置项。

v1.4.0 修正了 v1.3.0 自身的一个执行性缺陷。v1.3 给出的装配规程以 `shutil.copy(模板原件, 成品路径)` 开头，前提是工作区里存在模板 `.docx` 原件；但教师是在**知识库**中勾选模板的，而知识库的注入方式是「docx → 纯文本 → 写进消息正文」——表格被拉平成 ascii 框线，出现断字与解析残留，合并单元格、字号、颜色、页眉页脚在到达助手之前就已经丢失，更没有任何二进制文件落到文件系统。助手读得到模板**写了哪些栏目**，读不到它们**长什么样**，只能退回去新建文档，于是产出 9 张散表、235 段、0 处带颜色文字的"普通文档"。

换言之，v1.3 与 v1.2 犯的是同一类错误——**规程假设了一个当前条件下并不存在的前提**——尽管 v1.3 恰好新增了「规程不能要求助手做它做不到的事」这条设计说明。这说明该原则需要的不是重申，而是每条规程落地前的可执行性核查。

v1.4 的修法是把模板从知识库通道移到工作区文件通道（知识库那份保留，供语义），并补一条安全兜底：取不到 `.docx` 原件时**不交付任何 .docx**，改交逐栏内容清单。理由是重建出的文档看起来就是成品，教师很可能直接打印上交，到评审才发现结构不符——一份"看着对、结构错"的教案比没有教案危害更大，它制造虚假的完成感。同时新增一个零成本的机械判据：**成品中带颜色文字数为 0，即可判定它不是模板副本**（模板含淡红色说明文字），此项不通过时其余校验无需再做。

v1.5.0 来自助手对上一版的实证复盘，五条问题中四条成立。最要害的一条是：v1.4 把「带颜色文字数 > 0」写成了校验标准，但只是**描述**，没有**实现**——助手每轮现写校验脚本，而那份脚本里定义了取色函数却全文零调用，关键判据成了死代码，实际靠人工目测放行。同类问题还有：判断「推荐栏未被改动」用的是 `"此栏目为推荐标准" in ... or "双向闭环" in ...`，而模板该格原文本身就含「双向闭环」，于是改动与否都会通过——**判据恒真**。

至此三个版本重复了同一个失效模式：v1.2 要求助手检索知识库（无此能力）、v1.3 要求复制模板原件（原件不存在）、v1.4 要求校验带色文字（只给标准未给实现）。结论是描述式规程不足以约束执行，**校验必须以可运行的脚本随技能分发**，正文只许调用、不许现写。v1.5 因此新增 `scripts/` 目录，两个脚本均仅依赖标准库，不需要 python-docx。

另外两条：装配规程此前只演示了表格单元格，而本模板的学习目标、七个教学环节、小结梳理、作业布置、板书设计、教学反思共 36 个段落全在表格之外——只填表格会漏掉一多半内容，故补「双区装配」；模板中黑字与淡红字混排在同一单元格是常态（本模板至少 4 格，甚至把一个括号劈成两半），原先「黑保留／淡红替换」的两档规则落到混合格无从下手，故改为逐 run 判定。

未采纳的一条：助手称模板中不存在「此栏目为推荐标准，不改动」字样，建议把「（推荐）」栏视为应填。经核验该字样确实存在于 `r11c1`（教学框架）与 `r13c2`（全流程评价）两格的淡红说明中，`list_slots.py` 亦稳定标为 `[锁]` 2 格；若照其建议修改，会导致模板明令不得改动的两栏被填写。其方法层面的意见——判据应以 run 颜色为主、不硬编码具体字样——则予以采纳，因为换一个学科的模板措辞未必相同。

v1.6.0 有两处改动，都来自教师的现场判断。

其一，v1.5 随技能分发的两个校验脚本**在该平台无法装载**，技能目录只能是单个 .md。脚本化的思路在原理上成立，但落不到这个环境，故整体移除，全部自查项改写为肉眼可查的三件事：搜红字原句、比表形、点栏目名。

其二更重要：教师指出**模板里的红色字体在生成教案时是需要删除的**。此前各版把红字定义为"说明性文字，用实际内容替换"，对「待填」格而言结果相同，但对「锁定」格是错的——v1.5 规定「不改动」的格"跳过，一个字都不改"，这会让「（此栏目为推荐标准，不改动）」这句提示语原样印在交出去的教案上。正确规则是：**红字一律删除，无一例外**；「不改动」的含义是该格黑字正文保留、不另填内容，而不是整格原封不动。

这条修正还连带废掉了一个判据。v1.4 引入「成品带色文字数 > 0 即证明来自模板副本」作为零成本快速判据，并被 v1.5 列为先决项；但既然红字必须删光，**一份正确装配的成品颜色数本来就是 0**，该判据会把正确结果判成失败。判断是否模板副本，改看表形——课前要素表在模板中是一张跨多列、含纵向合并的大表，成品若变成简单两列或拆成多张散表，即可断定是新建文档。

值得记下的是这条判据的来历：它出自助手对自身产物的解剖（"0 处带颜色文字"），当时用来证明"这不是模板副本"是成立的；但把一个**在错误样本上有效的特征**直接反过来当作正确性判据，就不成立了。**错误的充分条件不等于正确的必要条件。**

v1.7.0 修的是一个由前几版累积造成的退化：**问答环节消失了。**

现场表现是，助手收到"帮我完成一个信息科技课的教案"后，一轮内做完了探查工作区、定标、装配、校验，18 次工具调用几乎全部花在找模板文件和编写生成脚本上——第 0 步的结构化表单没有发出，三个决策点一个也没问，教案直接产出。铁律 2（不代写）与铁律 8（单步推进）同时失效。

量一下章节字数就明白了：v1.6 中「模板处理规程」占全文 42.3%（4665 字符），而承载四步闭环与决策点的「工作流」只占 11.4%（1251 字符）——**装配规程是备课工作流本体的 3.7 倍**。连续四个版本修装配缺陷，把技能的重心从"备课决策"一路挪到了"文档工程"，助手读完得到的主要印象就是"这是个 Word 排版工具"。

另有一条规则在助推：v1.2 提出的「模板前置加载」，被理解成一开场就扎进文件系统找原件。问题在于"模板"被当成了单一对象，而它实际上有两个互不相干的部分：**栏目清单**（语义，知识库的纯文本就够，第 0 步即可用）与**版式原件**（二进制，只有装配那一刻才需要）。v1.7 将二者拆开，并以铁律 9 锁定顺序：第 0 步表单发出前不得读写文件系统，装配只发生在第 3 步末；模板原件缺失不阻塞第 0—3 步。

同时把「模板处理规程」压缩 63%（4665 → 1728 字符），使铁律与工作流重新成为正文主体（合计 42.6%）。

顺带解决了模板上传路径：平台的「我的文件」根目录对应助手可读的 `me/`，上传一次即对所有会话可见；对话框底部的文件区只写入当前会话工作区，换会话即失效——此前模板始终只在知识库，故助手历次清点工作区皆为空。

v1.8.0 的三条主要改动来自助手自己的归因，均经核验成立。

**其一，弹窗从未出现的原因是文档缺失。** SKILL.md 全文未出现过任何工具名：第 0 步写的是「直接给出表单」，第 1／2／3 步写的是「提出 1 个必须由教师回答的决策问题」——只说要问，没说用哪个工具问。该平台只有调用 `tool-ask-user` 才会渲染可点选卡片，规程不指定，模型便按默认习惯把问句写进正文，教师看到的只是普通文字。助手另交代了一层真实动机：它担心调用后本轮回合即结束会妨碍继续产出，又顾虑参数结构写错被拒，于是"退回到保险的纯文本"——**以降级方案规避工具，等于取消决策点**。故新增铁律 10，把决策点硬绑定到该工具，并明确禁止因参数顾虑而退回文本。

**其二，禁令的表述形式影响遵循度。** 铁律 9 是黑名单式表述（"第 0 步表单发出之前，不得读写文件系统"），位于正文第 139 行，其前 138 行已将注意力稀释。助手指出模型对"第一个动作必须是什么"这类白名单的遵循度明显更高。据此在正文最前端增设「首轮动作白名单」：首个工具调用只允许 `tool-ask-user`，第 0—3 步工具白名单仅此一项。

**其三，章节标题与正文自相矛盾时，标题赢了。** 第 0 步的标题此前是「结构化接单 ＋ 模板加载」，而其正文明写"本步不碰文件系统"。标题里的"模板加载"四个字持续诱导助手开场即翻文件系统。已改为「结构化接单（不加载模板、不碰文件系统）」。

另有一条由本方补入：**校验阈值不能留解释空间。** 本轮装配本身是成功的——成品 263.4 KB、表形与原件逐行一致、合并位全对齐，确为在原件副本上填空；但红字残留 12 处，助手将其自判为「均属模板声明项，按模板要求保留」而通过。该解释不成立：模板首页声明保留的是**黑字**，红字无论写着什么（包括「此栏目为推荐标准，不改动」）都是填表提示。这已是第三次同型放水——先是取色函数写成死代码，继而判据用 `or` 恒真，此次是为残留项提供豁免解释。三次的共同形态是**给检查留了一个解释空间**，故将该项改写为绝对阈值（红字数必须为 0），并明写不接受何种解释。

v1.9.0 修的是一个交互顺序陷阱，由教师在实际使用中发现。

助手在索取模板时会弹出选择框，选项写作「我把区/校教案模板 .docx 传到「我的文件」根目录（推荐）」。问题在于：教师点下选项的那一刻本轮即结束，助手立刻去检查 `me/`——而教师此时还没上传。**选项写成将来时，读起来像是在选一种打算，多数人会以为点完再去做；实际点击的语义却是"我已经传好了"。**

该故障已真实发生：助手在教师点选后随即报告「`me/**/*.docx` 命中 0，上传可能未生效，请在网页端确认」，促使教师去排查一个并不存在的上传故障——实际只是尚未上传。

根本原因是把一个需要前置动作的事塞进了弹窗：**弹窗只能承载「选择」，承载不了「先做一件事再选择」**。v1.9 据此补入一条通用规则（铁律 10 下）：凡选项的成立依赖某个外部动作，动作说明必须写在弹窗之前的正文里；选项一律写成完成时；必须给一个「还没做」的出口；条件不满足时的话术是等待（「传好回我一声」），不是质疑（「上传可能未生效」）。

同时把模板上传从流程末端的阻塞点，拆成「第 0 步非阻塞预告一次 ＋ 第 3 步末才真正检查」——预告不查文件系统、不等回复，只是让教师有充裕时间，避免推进到装配环节才措手不及。
